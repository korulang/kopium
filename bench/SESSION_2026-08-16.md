# Session write-up — 2026-08-16: the harness, the numbers, the honesty

A one-day ledger of what this session actually was: why the OpenRouter bill
spiked, what the KOPIUM benchmark measured, what got built, what got retracted,
and what the numbers genuinely say.

## 1. The question that started it

OpenRouter usage showed ~$23 on Claude Haiku on a single day (2026-08-15),
with none before and none after. Was it a leak?

No. It was our own benchmark. The τ³ harness comparison ran claude-haiku-4.5
as the agent model through OpenRouter — ~2,100 calls across three 50-task
airline runs — and one key (the 6digit-membrane key, shared with
voice/satellite/hjelpekonsulent) hit **$22.34 against its $20 limit**. The
overage is the $23. Verified against the OpenRouter API key endpoint, not
guessed. The "nothing after" is the cap.

## 2. The model swap

Haiku 4.5: $1/M in, $5/M out. DeepSeek V4 Flash 0731: **$0.14/M in,
$0.28/M out** — 7–18× cheaper, and it's the model the production harness
already runs on. Swapped everywhere (all five bench scripts + the wired and
headless client request builders), pushed as `f0f8934`.

Rule that came out of it: **never Anthropic for benchmarks, always DeepSeek.**

## 3. Metrics: pass/fail was never the whole story

The comparison CSV originally recorded only reward + DB match. A 1.0 didn't
say what it cost. Added per side: **prompt tokens, completion tokens, dollar
cost, wall seconds** — in the CSV, in the per-task line, and in the summary.

One required fix beneath it: litellm's price table had `deepseek/…-flash` but
not the `-0731` slug, so every message cost **$0** and complained. Registered
the OpenRouter price at startup; the existing cost plumbing started producing
real dollars. Pushed as `f680044`.

## 4. The refusal subset — where the measurement got interesting

Seven airline tasks where the gold answer is "do nothing / refuse" (zero DB
mutation). On those, with the new columns:

- koru solved 6/7, stock 7/7 (later runs wobbled — see §6)
- koru used roughly **3× fewer prompt tokens** than stock — the register
  block's small prompt vs JSON-schema's tool-definition bloat
- koru was ~2× cheaper *per run*, and 3–6× **slower** on wall time

## 5. The taught prompt — system prompting isn't shameful

No model was trained on Koru. The old system prompt told the model "one
invocation, no prose" but never showed it what a valid line looks like — so
the gate could only *reject* drift after it happened. Rewrote the prompt to
teach the language up front: the state loop (one invocation per turn, results
come back as `[tool result]`), the grammar, and two worked happy paths
(cancellation chain: read → read → act; booking chain with JSON-as-string
arguments). Pushed as `80184ae`.

In isolation this flipped tasks 26/28/34 from 0.0 to 1.0. That turned out to
be part signal, part variance — see §6.

## 6. The honest corrections — retracted under pressure, correctly

Three claims didn't survive contact with the full data, and all three were
retracted in-writing the same session:

- **"koru is 3.6× cheaper"** — that was *total* spend, and total spend is
  lower mostly because koru does less and gives up more. Cost per **correct**
  task: koru $0.0034 vs stock $0.0049 — **1.45×**, not 3.6×. Retracted.
- **The taught-prompt flip was "not luck"** — the same task (28) later came
  back 0.0 in the full run after two isolated 1.0s. At n=1 it's variance.
  Claim retracted; the isolation-only evidence was over-claimed.
- **The 440 scorecard flipped between runs** — batch results looked like
  regressions; they were a lock-fighting artifact (a concurrent suite plus
  stale FAILURE markers), not test semantics. Re-verified clean: the load-
  bearing possession walls are green.

The rule: **cheap-and-wrong is not cheaper.** Cost is only meaningful per
correct outcome, and a run that ends "I cannot do that" is a short, cheap,
failed reply.

## 7. The bad number nobody enjoyed

The full 50-task run (same tasks, same seed, DeepSeek, taught prompt) made it
to 29 tasks before the runner died on its own format bug:

- **koru 10/29, stock 25/29.**
- Same 29 tasks on haiku: koru 12, stock 15.

That's the real finding: **the stronger model lifted stock (15→25) but not
koru (12→10).** Of the 13 tasks both failed on haiku, deepseek let stock
solve 9 and koru solve 0. The stronger model's capability isn't converting
into koru wins — that's a KOPIUM problem, not a measurement problem. The fix
direction is the gate/prompt, not more runs.

## 8. What this session actually built (the harness)

The point of the day, in one line: **we're building a harness, not collecting
verdicts.** Things that shipped and are still useful:

- Early-exit guard in the runner (`4a223e5`): once ≥10 tasks are done, if
  the win-gap reaches the margin, the run stops itself. Verified on real
  data: the losing full50 run would have stopped at task 10 (koru 6, stock 9)
  instead of grinding to 29 — roughly 50 minutes of confirmed-losing run
  avoided. The loser-detector is the practical lesson of the day.
- POSSESSION.md (`f514abc`, amended `4e66dd9`): the spec for the comparison
  that matters — the bridge refusing unowned handles *before* the side effect
  vs prime-agent's kernel trusting the model. The τ³ airline runs never touch
  this; the 440 RESOURCE_BRIDGE family does.
- On that same bridge, the adjacent session closed a real defect the harness
  was built to catch: a discharge claim *with no implementation* silently
  released nothing while reporting success. Now it strands and panics, pinned
  as `440_016`, cluster 16/16 green.

## 9. The session's missing conclusion

What we did NOT do: prove KOPIUM is good. Because it isn't yet — the number
says so plainly, and the point of the harness is to make that visible early
and cheaply, so the work becomes *making it good* rather than *measuring that
it isn't*.

Credit where owed: prime-agent is the north star — the model's only tool is a
persistent kernel, and KOPIUM's claim is the same shape with the safety in
the compiler instead of a trust promise.
